# Brevo account access and library email

## Deploy in this order

1. Back up the database. Apply `db/migrations/2026-10-21-emailjs-account-recovery.sql` on one database connection with a SQL client that stops on errors. It uses a temporary table, without stored procedures or `DELIMITER`. Its preflight rejects duplicate normalized email addresses before changing tables; resolve conflicts explicitly. Do not run `fresh-start.sql` on an existing installation.
2. Copy `backend/email.env.example` values into the backend environment. Generate a 32-byte encryption key; keep it outside source control and retain it across restarts. The key also protects challenge HMACs; replacing it requires fresh invitations/recovery requests. Leave `EMAIL_ENABLED=false` until configuration is ready. Schema changes are required even when sending is disabled.
3. In Brevo, verify the sender address and authenticate its domain. Create an API key under Settings > SMTP & API (not an SMTP key). Set `BREVO_API_KEY`, `BREVO_SENDER_EMAIL`, and optionally `BREVO_SENDER_NAME` in the backend environment. The backend sends to the transactional API using locally rendered, escaped HTML and plain text; no dashboard templates are needed. Review provider log retention and tracking settings for sensitive account emails.
4. For local work use `EMAIL_MODE=capture`, `EMAIL_ENABLED=true`, and an encryption key. The adapter exposes an in-memory `capturedEmails` array to local test code only; there is no public capture endpoint and nothing secret is logged. Production rejects capture mode and requires an HTTPS public application URL.
5. For live delivery use `EMAIL_MODE=brevo` and `EMAIL_ENABLED=true`. Set `EMAIL_DAILY_LIMIT=300` for Brevo Free. The application derives a new UTC day automatically, with no manual period dates. Its counter resets at 00:00 UTC (08:00 Philippine time). Preserve `email_quota_usage` when deploying or restoring. Brevo enforces its own account-wide credits separately. The official free-plan documentation confirms a daily reset without specifying the timezone; UTC is the application counter boundary, not a provider credit synchronization guarantee.
6. Restart the backend. Test an invitation, verification, recovery code/reset, and summary to controlled representative mailboxes. Check inbox/spam, code expiry, link fragments, and delivery status. Local builds and mock tests do not establish live deliverability. Enable personal notices/digests only after these checks by setting `EMAIL_ROUTINE_ENABLED=true`. Account workflows use `EMAIL_ENABLED`; routine generation additionally requires `EMAIL_ROUTINE_ENABLED`.

Use a dedicated Brevo key/account to make provider usage easier to reconcile. The application conservatively counts every dispatched API attempt, including unknown outcomes; its counter can exceed provider consumption. Current default: 300 attempts per UTC day, with the final 50 reserved for account/security emails. Routine mail pauses at 250 total attempts; account mail can continue until 300. Quota-paused mail waits until the next UTC midnight and is rechecked for expiry and eligibility before sending. Unused allowance does not carry over. Bulk announcements are in-app by default and can opt into email. Lower the routine allowance by increasing the reserve if account access needs the whole budget.

## Migrating an existing EmailJS installation

Stop the backend worker during the configuration switch. Keep the existing database, `EMAIL_ENCRYPTION_KEY`, and usage counters. Remove `EMAIL_MONTHLY_LIMIT`, `EMAIL_QUOTA_PERIOD_START`, and `EMAIL_QUOTA_PERIOD_END`; add `EMAIL_DAILY_LIMIT=300`. Historical quota rows remain intact; if an old period started on the current UTC date, that recorded usage is conservatively counted for today. Change `EMAIL_MODE=emailjs` to `EMAIL_MODE=brevo`, add the three `BREVO_*` settings above, and remove the obsolete `EMAILJS_*` settings. Restart after installing this code. No new SQL migration is required if the email schema is already installed; the historical migration filename stays unchanged.

Queued messages use the same provider-independent encrypted format and will be sent through Brevo if still eligible and unexpired. Accepted messages stay accepted. Unknown outcomes still require manual review before a fresh request, because a previous provider may already have accepted them. The example environment intentionally starts disabled in capture mode; do not overwrite an existing encryption key with a generated replacement.

Brevo Free includes 300 sends per day with no rollover: [official free-plan limits](https://help.brevo.com/hc/en-us/articles/208580669-FAQs-What-are-the-limits-of-the-Free-plan). Sends from other applications or the Brevo dashboard share provider credits but are not included in this application counter.

## Manual notification email

Admins and super admins can select **Also send by email** when composing individual, role-wide or library-wide notifications. It is off by default and requires both `EMAIL_ENABLED=true` and `EMAIL_ROUTINE_ENABLED=true`. The preview separates in-app recipients from active, setup-complete users with verified email addresses. Its daily capacity estimate subtracts attempts already used and queued routine emails while protecting the security reserve; it does not reserve credits or include other Brevo applications.

Apply `db/migrations/2026-10-27-manual-notification-email.sql` once before deploying this feature. Alternatively, run `npm --prefix backend run migrate-manual-email -- --apply`; the runner adds only missing columns/indexes and can resume after partial DDL. Running it without `--apply` checks schema readiness. Existing notifications remain in-app only. Keep the historical migration order and back up an installation before schema updates.

Immediate publication commits its notification, frozen email recipients and durable handoffs together. Scheduled notifications resolve recipients when published, so compose counts are estimates. No provider request runs during publication. One delivery is queued per eligible recipient, with routine priority. The existing worker applies the daily cap, retries explicit rate rejections, and defers overflow to the next UTC day. Delivery rechecks verified ownership, account state, role membership, notification activity and expiry. It never substitutes a changed address or adds new recipients after publication.

Unsent emails expire seven days after publication or at the notification's explicit expiry, whichever comes first. Expiring a notification cancels unsent emails; emails already accepted cannot be recalled. Resend opens a new compose form with email unchecked. Replayed scheduled jobs reuse the publication key; email retries keep their original identity. Unknown outcomes require review, with no automatic resend.

Notification details expose queued, processing, accepted, failed, unknown and cancelled counts to admins and super admins. They do not expose recipient addresses. The global email-delivery log remains super-admin-only. Acceptance does not confirm inbox delivery. Restored queue events suppress email and restore cancels pending/failed deliveries; notification batch identifiers prevent a reused notification ID from creating duplicate emails.

The added API is `GET /api/admin/notifications/email-preview` with the existing audience fields. Creation accepts optional boolean `sendEmail` (default false) and `confirmedEmailCount`; opted-in immediate sends validate both confirmed counts again within the publication transaction. Preview returns `inAppCount`, `emailCount`, `skippedCount`, enablement/reason, daily usage, pending routine count, remaining routine capacity and the UTC reset timestamp. Notification details add `email_requested`, `email_expires_at` and `email_summary`.

### Manual email verification

Run `node -r ts-node/register test/notifications.email.test.js` through the normal backend suite. For real SQL checks, `node -r ts-node/register scripts/prepare-manual-email-test.ts` creates empty table copies in the fixed local `euc_manual_email_test` schema; run `test/notifications.email.database.integration.test.js` with `DB_NAME=euc_manual_email_test` and `RUN_DB_INTEGRATION=1`. Fixtures are removed after each test and provider delivery is captured. No library records are copied or modified. The frontend component tests cover opt-in, preview states and delivery results; `node scripts/verify-manual-email.mjs` checks the full desktop/mobile flow against a Vite server on port 4175, intercepting all API calls with synthetic responses.

## Account behavior

Every newly created account needs a valid unique email. Staff cannot submit passwords; creation queues a 24-hour invitation and denies normal login until setup. Setup verifies email and clears the first-password gate. Legacy accounts retain passwords and access; historical email starts unverified and cannot receive routine notices or recovery. Existing populated email cannot be cleared. Changed addresses stay pending until confirmed; setup-pending accounts instead receive a replacement invitation at the corrected address.

Recovery uses a six-digit code valid for 10 minutes, five attempts, a 60-second resend cooldown, and five requests per email per hour. IP middleware also limits public endpoints; database counters survive restarts. Successful code verification grants a separate single-use 10-minute reset token. Setup/reset/verification tokens are purpose-bound. Setup/reset uses a POST; merely opening a link does not consume it. Passwords are 8 characters minimum and 72 UTF-8 bytes maximum for bcrypt. Password recovery revokes refresh sessions and invalidates old access tokens through per-account versions; active local WebSockets close immediately and other instances check periodically.

Public endpoints under `/api/auth`: `setup-password` (`id,token,password`), `verify-email` (`id,token`), `recovery/request` (`email`), `recovery/verify` (`email,code`, returns `id,token`), `recovery/reset` (`id,token,password`). Authenticated endpoints: `email-status`, `email-verification`, `email-change` (`email`). Account management: `POST /api/admin/users/:identifier/account-email` with action `invite`, `verify`, or `recovery`, subject to existing role hierarchy. Super-admin-only delivery status: `GET /api/admin/email-deliveries`; retry eligible failed routine deliveries with `POST /api/admin/email-deliveries/:id/retry`.

Bootstrap a fresh super-admin through the existing seed, then attach a real email and issue an invitation using `npm run invite-super-admin --prefix backend -- <username> <email>`. This command is intended for the deployment operator with database/environment access; it invalidates the existing password/sessions. It never prints the invitation secret. Existing users who lose mailbox access need staff-assisted contact correction and new verification. There is no staff password bypass.

## Persistence and failure handling

Email outbox records are handed off to a separate persistent delivery worker. The worker uses a database named lock shared with restore and a shared 1.1-second rate slot, so multiple instances cannot send concurrently. Authentication has priority. Routine delivery never gates a completed circulation transaction or the in-app notification. A delivery's deduplication key prevents repeat queue entries. Summary keys are per user/Manila date; reminders consolidate all their overdue loans, including zero-fine loans, and cancel when none remain. No previous-day catch-up is sent. Routine events expire after 24 hours.

HTTP 201 means accepted by Brevo, not confirmed inbox delivery. Provider message IDs are not currently stored. Explicit 429 rejection retries with backoff, up to five attempts. Permanent errors stop. Timeouts, uncertain server failures, and abandoned processing rows become unknown and are not automatically resent. This adapter does not use provider idempotency keys. Queue-level deduplication cannot guarantee exactly-once external delivery. Inspect unknown outcomes before requesting a fresh invitation or recovery code. Failed routine emails can retry only while still eligible and unexpired; secrets are scrubbed on terminal authentication outcomes. Successful and cancelled content is scrubbed.

Quota windows and rate state are operational data. Challenge, delivery, request-limit, address-claim, rate, and quota tables are excluded from application snapshots. Restore acquires the dispatch lock, invalidates challenges, cancels pending emails/outbox handoffs, suppresses email fanout from restored notification jobs, and rebuilds email claims from restored accounts. Live quota accounting remains intact. Restoring cannot revoke an email already accepted before the restore started.

No delivery webhooks or bulk-email controls are implemented. Delivery logs contain no template variables or credentials. Configure sender verification and domain authentication in Brevo. API details: [Brevo transactional email reference](https://developers.brevo.com/reference/send-transac-email).

## Validation

Run backend `npm test` / `npm run build`, and frontend `npm test` / `npm run build` / `npm run lint`. Optional database tests require `RUN_DB_INTEGRATION=1`, a dedicated database whose name ends in `_test`, and the current schema. Never point fixture tests at a live library database. Live Brevo tests require real credentials and consume quota.
